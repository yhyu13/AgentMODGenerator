## client.py Fixes

### 1. Line 60 — Empty API key validation
**Problem**: `api_key=api_key or os.environ.get("OPENAI_API_KEY", "")` passes empty string to client, causing silent auth failures.

**Fix**: Validate non-empty before passing to `AsyncOpenAI`.

```python
# In OpenAIClient.__init__:
_openai_key = api_key or os.environ.get("OPENAI_API_KEY", "")
if not _openai_key:
    raise ValueError("OPENAI_API_KEY is not set or is empty")
self._client = openai.AsyncOpenAI(api_key=_openai_key, ...)
```

### 2. Lines 76, 103, 137 — Unguarded `response.choices[0]`
**Problem**: `response.choices[0].message.content` raises `IndexError` if choices is empty.

**Fix**: Add guard before access.

```python
if not response.choices:
    raise LLMError("OpenAI response has no choices")
content = response.choices[0].message.content or ""
```

### 3. Line 139 — Unhandled JSONDecodeError in fallback path
**Problem**: `_complete_with_fallback` calls `json.loads(content)` without try/except.

**Fix**: Wrap `json.loads(content)` in try/except inside `_complete_with_fallback`.

### 4. Line 165 — Unguarded `response.content[0].text`
**Problem**: `response.content[0].text` raises `IndexError` if content list is empty.

**Fix**: Add guard.

```python
if not response.content:
    raise LLMError("Anthropic response has no content")
return response.content[0].text
```

### 5. Line 188 — Falsy API key bypasses provider detection
**Problem**: `if os.environ.get("ANTHROPIC_API_KEY")` — falsy values like `"0"` or `""` evaluate as falsy, skipping detection.

**Fix**: Use explicit empty string check.

```python
anthropic_key = os.environ.get("ANTHROPIC_API_KEY", "")
openai_key = os.environ.get("OPENAI_API_KEY", "")
if anthropic_key:
    return AnthropicClient()
if openai_key:
    return OpenAIClient()
```

### 6. Line 150 — Same empty API key issue for Anthropic client
**Fix**: Same validation pattern as #1 for `ANTHROPIC_API_KEY`.

## llm_utils.py Fixes

### 1. Line 85 — Thread-unsafe get_client() per-invocation
**Problem**: `get_client()` is called on every `generate_structured()` and `generate_text()` invocation, creating a new client each time.

**Fix**: Use module-level cached client instance with thread-safe initialization.

```python
_client: CompletionClient | None = None
_client_lock = threading.Lock()

def _get_cached_client() -> CompletionClient:
    global _client
    if _client is None:
        with _client_lock:
            if _client is None:
                _client = get_client()
    return _client
```

Update `generate_structured()` and `generate_text()` to use `_get_cached_client()` instead of `get_client()`.

### 2. Lines 90-93 — Deadlock risk with nested asyncio.run()
**Problem**:
```python
future = loop.run_in_executor(None, lambda: asyncio.run(_run()))
return future.result()
```
`asyncio.run()` creates a new event loop; `future.result()` blocks the outer loop waiting for the inner loop to complete — classic deadlock.

**Fix**: Use `loop.run_until_complete()` directly on the coroutine, not in an executor.

```python
try:
    loop = asyncio.get_running_loop()
except RuntimeError:
    # No running loop - create new one
    loop = asyncio.new_event_loop()
    try:
        return loop.run_until_complete(_run())
    finally:
        loop.close()
else:
    # Running loop exists - create a future to schedule work
    import concurrent.futures
    with concurrent.futures.ThreadPoolExecutor() as pool:
        future = pool.submit(asyncio.run, _run())
        return future.result()
```

Or simpler: avoid the executor pattern entirely since `_run()` is already async:

```python
# This will deadlock, so use ThreadPoolExecutor to run asyncio.run() in a separate thread
with concurrent.futures.ThreadPoolExecutor() as pool:
    return pool.submit(asyncio.run, _run()).result()
```
